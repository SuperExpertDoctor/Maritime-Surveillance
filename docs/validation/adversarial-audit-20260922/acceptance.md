## 空正文诊断与修复

另一次直接供应商诊断为 `finish_reason=length`、输出预算 4096 tokens 用尽、正文长度 0、无 refusal；8192 tokens 的跟进诊断在 120 秒超时。第一份诊断额外请求了 JSON 格式，仅用于确认供应商存在“截断且无正文”的响应类型，不等同于重放原生产请求。最终生产重跑也直接捕获到 `LLMOutputTruncated`，证明此问题不仅出现在额外诊断条件下。

原网关仅提取 content，忽略 finish_reason，使截断误报为 JSON 格式错误。现在拒绝任何 `length` 结束的响应，在既定三次尝试及共享截止时间内最多增至初始预算四倍、绝不超过 16384 tokens。每次预算和截断原因都有审计记录，不输出思考内容，不执行被截断的合法 JSON 片段。

关闭思考所用 `thinking: {type: disabled}` 与[供应商官方接口](https://longcat.chat/platform/docs/api/chat.html)一致。增加输出预算不能保证克服服务超时；真实稳定性必须读取最终重跑结果，不能由这项补丁推定。

## run5 暴露的搜索抢占漏洞

run5 的 `report.passed=true` **仅指脚本列出的八项运行连通性检查**，不代表全部功能、传感效果或无故障验收。报告内部 `summary.episode_outcome.valid=false`，原因 `decision_maker_failed`；SAR 累计为 0，没有已完成的目标识别/稳定跟踪。被动传感记录 3 条方位、1 次联合定位。真实墙钟 497.440 秒，不是等待或拼接运行。

读取第 32 分钟快照发现 `desired_search_count=10`、`active_search_count=10`、`required_new_search_count=0`，模型仍一次抢占 8 架搜索飞机，原校验器允许。第 39 分钟又抢占 1 架，剩余 1 架转场，解释本轮后半段搜索停滞。不是单纯等待飞机到达就能解决。

新增修复：快照不再暴露会打破搜索保底的抢占；校验器检查“现有+可匹配待执行+新增−抢占”后的保留预算，即使整体资源不足也不允许进一步恶化当前搜索保底。两条失败测试先复现，再以 115 条相关测试通过验证。提示明确零新增配额不代表可移除已有搜索。

修复后独立真实重跑为 `run6`。run5 保留原始证据，不重新标记成已包含此补丁的最终结果。额外的 120 步固定人口 fixture 仅作算法补充，不代替真实模型证据。
