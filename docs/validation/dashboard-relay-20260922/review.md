# 地图数据接口、改降与接力跟踪复核

基线：main `f385260`。本轮修改尚未提交。

验收范围：

1. 原预约基地的返航路径失效时，评估其他基地的实际安全航程、剩余航程与容量；成功后转移预约，无可行方案才失败。
2. 核查前端消费的 HTTP/WS 接口，以及时间线、区域、模型日志、参数、AIS 五个面板的数据来源与场景隔离。
3. 模型决策结果、说明和外部 API 实际返回的推理字段分别显示；缺失必须明确，不能将普通说明冒充 think。
4. 旧 UAV 退出跟踪后，基于最后有效观测保留证据并生成重捕获需求；新 UAV 搜索并实际发现后才能继续跟踪。禁止用目标真值坐标或交接事件伪造 SAR 覆盖。
5. 完成修复后使用真正的 `main.py`、真实模型、HTTP 服务和 WS，在独立目录记录至少 1200 秒墙钟验证。暂停、重试、模型失败、自然未触发的功能都单独记录，不充作验证成功。

新增运行参数：`--wall-seconds` 在当前仿真步结束后检查墙钟期限；不取消进行中的模型请求，因此实测运行可超过指定期限。`--run-report-dir` 只接受新的目录，记录最终摘要、模型调用元数据和事件；不写请求凭据和原始提示。暂停期间不生成虚假推进帧，运行报告保留收尾前状态。入口相关回归目前 29 passed。

最终真实运行结果见文末。

## 运行中发现并修复的事件边界问题

第一轮真实 main.py 运行至 985.84 秒主动停止，不计作 20 分钟验收。发现步间应用的重点区/船舶命令虽然有成功回执，却被帧构建器 `(now-1, now]` 时间过滤排除，时间线因此漏事件。先增加失败回归，再让正式 HTTP/WS 和帧记录保留最近 300 条已发生事件；前端按事件 ID 去重，回放不读取未来事件。直接 build_frame 的默认调用约定保留。

修复后相关 65 项通过；加入初始 WS 的有界历史及未来事件检查后，决策/API 套件 7 项通过；真 FastAPI/构建版 React 夹具集成再次 1 项通过。之后才启动第二轮完整 1200 秒运行，其实现代码全程冻结。运行期间仅修正上述调度器测试的日志捕获方式、更新文档。

第二轮 monitor 的重点区 CRUD、II 类船舶增删及 AIS 开关，在约 41.75 秒完成全部回执/状态验证；后续 WS 帧中也能读取这些命令对应事件。生产浏览器五面板初次检查 1 passed。
